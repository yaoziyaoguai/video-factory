# Visual Asset Pipeline Design

## Problem

The current renderer proves that VideoFactory can produce an MP4, but the output is a text-card preview rather than a publishable short video. Loop 6 upgrades the system so every production render prefers real stock imagery or footage and records enough licensing metadata for human review.

## Goals

- Add a provider boundary for free stock assets, starting with Pexels and Pixabay.
- Keep API keys out of git; read them from environment variables only.
- Write a per-job asset plan containing provider, source URL, creator, license note, media type, dimensions, download URL, and local path.
- Render with downloaded video/image assets when available.
- Mark no-asset text-card output as preview/fallback, not publish-ready.

## Non-Goals

- No automated platform posting.
- No paid stock providers.
- No CAPTCHA, account creation, or API key creation without user action-time confirmation.
- No committed downloaded media or secrets.

## Architecture

`stock_assets.py` owns provider search, normalized candidate records, download helpers, and asset plan creation. `renderer.py` consumes the asset plan and renders scene clips by combining the background asset with a transparent caption overlay generated by Pillow. The CLI wires this into `asset-search`, `prepare-assets`, and `render-job --require-assets`.

## Provider Order

1. Pexels: first choice for vertical stock video when `PEXELS_API_KEY` exists.
2. Pixabay: second choice when `PIXABAY_API_KEY` exists.
3. Local asset plan: useful for testing and manual curation.

## Quality Gate

When `render-job --require-assets` is used, every scene must have a usable local image or video asset. If any scene is missing an asset, rendering fails with a clear message. Without `--require-assets`, renderer may produce a preview fallback, but the manifest must include `visual_quality: preview`.

## Browser/API Key Handling

The browser can be used to open provider key pages, but the final action of creating an API key or account must be confirmed by the user at action-time. If login, CAPTCHA, email verification, or phone verification blocks progress, record it as a support item and continue the local engineering work.
