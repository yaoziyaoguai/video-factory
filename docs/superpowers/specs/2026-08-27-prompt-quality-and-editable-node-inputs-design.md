# VideoFactory 提示词质量与节点可编辑设计

## 目标

VideoFactory 不能只保证模型返回合法 JSON。它必须让每个角色交付可制作、可审计、可修改的内容，并能解释最终画面为什么采用某个模型、素材和提示词。

本轮成功标准：

1. 每个模型节点展示角色、Provider、模型、Prompt 版本、实际输入、实际 Prompt 和结构化输出。
2. 每个节点的业务输入和输出都能保存为人工版本；原始版本、执行凭证和成本证据不可篡改。
3. 人工修改输入后，当前节点和全部下游自动过期；人工修改输出后，全部下游自动过期。
4. 进入按量付费节点前，授权必须绑定最新输入版本、模型、费用上限和最大尝试次数。
5. 脚本、导演和审片不再只校验字段完整性，还校验观众承诺、可见动作、素材可得性、镜头变化和意图兑现。
6. Prompt 通过固定样例回归测试，模型或 Prompt 版本变化不能无声进入生产。

## 当前问题

现有样片暴露了四个独立问题：

- 编剧把四个叙事段落直接等同于四个六秒镜头，导致后三段成为长时间静态卡片。
- 导演方案的文字完整，但缺少逐秒动作和可验证的镜头成功条件，生成视频没有兑现拉帘和光影变化。
- 模型生成 Prompt 混入合规说明和工作流元信息，真正需要模型执行的主体、动作、时间和运镜反而不够突出。
- 视觉审片只看关键帧，不读取脚本和导演意图，因此能发现“静态”，却不能判断“承诺的动作是否出现”。

## 角色与 Prompt 分层

每个角色的 Prompt 由五层组成，按稳定到易变排序：

1. `identity`：角色职责、决策边界、禁止事项。
2. `deliveryContract`：上游输入、必须做出的判断、输出字段和下游验收标准。
3. `templateContext`：题材模板、平台、观众、时长、成本、事实与版权约束。
4. `examples`：少量高质量和反例，覆盖热点、知识、照片、产品、人物等不同输入。
5. `taskData`：本次真实数据，始终与指令分隔，防止输入内容覆盖系统规则。

Prompt Pack 使用显式版本，例如 `video-factory/screenwriter-v3`。模型 ID、Prompt 版本和实际 Prompt 一起写入不可变的 `model_trace` 产物。

## 角色交付合同

### 选题总编

先判断“值得做视频吗”，再提出角度。输出除热度外必须包含：视觉可表现性、证据可得性、观众收益、系列潜力、版权/政治/灾害风险和不做视频的理由。高热度不等于高视频价值。

### 创意编剧

先写一句观众承诺，再设计叙事节拍和镜头节拍。故事段落与镜头不是一一对应关系。每个镜头必须包含：

- 旁白和屏幕文字；
- 观众实际看见的主体、动作与变化；
- 镜头目的、建议时长、声音提示；
- 成功条件和失败条件；
- 可检索短词，不把生成 Prompt 当检索词。

24 秒内容默认需要 6 到 10 个视觉节拍；除有意停顿外，连续静态画面不得超过 3 秒。

### 视觉导演

先建立视觉母题、连续性锚点和转场语法，再逐镜路由。每个生成镜头输出中性 Shot Spec，而不是直接拼一段厂商 Prompt：主体、环境、动作、时间节拍、景别、机位、运镜、光线、材质、氛围、连续性锚点、负面约束、参考素材需求和成功条件。

Provider Compiler 再把 Shot Spec 编译为 MiniMax、Seedance、Seedream 或图库查询。合规标识、版权记录和工作流说明不进入生成 Prompt，由渲染与发布层处理。

### 素材导演

先验证所选素材是否满足镜头成功条件。找不到真实证据素材时进入人工替换，不用漂亮但无关的图填空。生成视频优先采用首帧/参考图保持主体和风格一致；纯文生视频只用于不依赖身份连续性的镜头。

### 声音导演与剪辑师

声音交付包含句级表演指示、停顿、重音、环境声和音乐进入/退出点。剪辑交付包含每个视觉节拍的时间线、转场理由和字幕安全区；不允许把多张同构信息卡当作“完成剪辑”。

### 视觉审片员

同时读取关键帧、脚本、导演 Shot Spec 和时间线，检查：意图兑现、前六秒留存、构图、连续性、视觉变化、文字可读性、音画对应和安全。每条问题绑定时间码、预期、实际观察和可执行修改。

## 节点输入与输出版本

每个 `NodeRun` 增加独立的 `inputState`：

```ts
interface NodeInputVersion<TInput = unknown> {
  id: string;
  nodeId: string;
  source: "derived" | "human";
  value: TInput;
  upstreamVersionIds: string[];
  parentVersionId?: string;
  createdAt: string;
  createdBy: string;
  schemaVersion: string;
}

interface NodeInputState<TInput = unknown> {
  effectiveVersionId: string;
  stale: boolean;
  versions: NodeInputVersion<TInput>[];
}
```

规则：

- 首次执行前保存 `derived` 输入版本。
- 人工编辑保存 `human` 输入版本，不覆盖历史。
- 重跑时使用有效人工输入；用户可以选择“恢复跟随上游”生成新的 derived 版本。
- 上游变化时，人工输入不被偷偷替换，但标记为过期，必须再次确认或恢复跟随。
- 成本授权绑定有效输入版本和全部上游有效输出版本。
- 二进制产物通过替换、裁剪或重新生成编辑；JSON、文字和参数使用结构化编辑器。

## Studio 工作区

每个节点展开后提供五个页签：

1. `输入`：可读预览、完整 JSON、编辑、恢复跟随上游、版本历史。
2. `角色与模型`：角色职责、Provider、模型、计费类型、Prompt Pack 版本。
3. `实际 Prompt`：模型实际收到的 Prompt；图片只显示文件名、时间码和哈希，不内嵌二进制。
4. `输出`：结构化预览、媒体预览、编辑或替换、版本历史。
5. `执行证据`：请求编号、耗时、成本、授权、校验结果，只读。

## Prompt 回归

仓库保存不含敏感信息的固定样例：热点事实解读、生活知识、照片故事、产品教程和人物微纪录。测试分三层：

- 静态合同测试：Prompt 版本、必需段落、Schema 和数据隔离边界。
- 输出验证测试：镜头数量、视觉变化、时间总和、可见动作、Provider 能力和预算。
- 模型抽样评测：只在人工触发时调用订阅模型，对多个 Prompt 版本盲评；不在 CI 中产生费用。

## 发布顺序

1. 先升级 Prompt Pack、脚本/导演/审片合同和模板镜头密度。
2. 再实现输入版本模型、Studio 五页签和实际 Prompt 追踪。
3. 使用已经购买的 MiniMax 素材重新编排，不新增付费调用。
4. 通过技术质检、Codex 与 GLM 交叉审片、人工浏览器验收后才生成发布包。
