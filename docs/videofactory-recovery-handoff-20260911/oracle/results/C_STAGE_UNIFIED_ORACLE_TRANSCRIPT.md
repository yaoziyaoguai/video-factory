### CG-01｜P1｜追加命令没有以已准备记录作为恢复时的唯一载荷

**位置：**`studio-c2-quote.ts::amendProductionScope`，节选第 133–240 行；`pipeline-c1-host.ts::acceptProductionAuthorization`，节选第 26–38、61–88 行。

**当前行为：**追加命令写入 `prepared` receipt，其中已经保存了完整 `scope`；重放却只读取 `digest/status/authorizationId`，随后重新构造 amendment，并重新生成 `approvedAt`。与此同时，宿主只允许已有未提交授权文件与新请求的内容**完全一致**。

原方法的内存故障注入复现了两个窗口：

* **授权文件写完、run CAS 前中断：**重放使用同一个授权 ID，却带着新的 `approvedAt`，被拒绝为 `already been accepted with different state`，run 仍未接受授权。
* **run CAS 后、自动续链前中断：**重放发现该授权已是 head，直接返回当前 run；该恢复分支没有重新完成续链，仍停在 `awaiting_spend_approval`。这是所附方法的恢复缺口；其他入口是否另有补偿，需要完整宿主核验。

**必须达到的合同与根因：**同一个已准备命令必须重放同一个不可变载荷；“授权已提交”和“命令后续动作已完成”不能混为一谈。当前实现把“重新计算命令”和“检查当前 head”当成了恢复。

**唯一修复方向：**以 prepared receipt 中保存的 scope 为恢复权威，不重新生成时间、身份或授权条款；按该命令对应的 committed authorization 核对提交结果，再通过原 governed continuation 完成未完成的续链，同时遵守暂停及 accepted/unknown 请求恢复规则。旧命令已被后续授权 supersede 时，也应识别其历史提交结果，而不是重新签发。

**最小回归集：**prepared 后中断；授权文件后/CAS 前中断；CAS 后/续链前中断；续链后/accepted receipt 前中断；同 key 不同参数拒绝。另覆盖重放时已暂停、旧命令已被后续授权替代、receipt 损坏不得被解释为空记录。所有窗口断言授权唯一、delta 一次、原载荷不变、新媒体 create 不重复。

### CG-02｜P1｜“严格链校验器”只检查幸存者数量，不验证完整授权链

**位置：**`pipeline-c1-host.ts::inspectProductionAuthorizationChain`，节选第 285–315 行；接受与读取的调用路径。

**当前行为：**校验器解析各文件、检查 `runId`，然后统计未被 supersede 的记录。它没有验证前驱存在、链无环、所有 committed 记录属于同一条链，以及文件身份与 `scope.id` 的一致性。原函数反例中，下面两种状态都返回了 `committed`：

```text
只有 A，且 A.supersedesAuthorizationId = MISSING
存在 A，以及与 A 无关的 B→C、C→B 环
```

两种情况都只有一个“幸存者”，但都不是合法授权链。

此外，读取路径的 artifact SHA 校验位于该 helper **外部**，接受路径传入的只是 committed IDs；因此“共用同一 helper”并没有建立“共用同一内容完整性校验”。接受路径是否另有通用事务层补验，需要完整实现确认，不能从本节选宣称两侧已经等价。

**必须达到的合同与根因：**唯一 head 是必要条件，不是完整链的充分条件。损坏的 committed 链必须在接受新授权前 fail closed，不能先改状态再依赖消费侧报错。

**唯一修复方向：**让唯一校验器消费 committed artifact 记录，统一完成路径/ID/内容摘要校验；从同一份已校验字节解析 scope；从唯一 head 沿 predecessor 遍历，要求无环、无缺失前驱且覆盖全部 committed 授权。保留对未提交 orphan 文件的独立恢复语义，不把它们混入 committed 链。

**最小回归集：**合法单授权及多级追加链；缺失前驱；独立循环分量；多 head；文件 ID/内部 ID 不符；保持合法 JSON/schema 的金额篡改；正常未提交 orphan 恢复。非法状态下接受与读取均拒绝，接受失败不新增 artifact、不推进 revision。

### CG-03｜P1｜结构化费用评估没有计算整份计划，可能错误引导追加

**位置：**`production-authorization.ts::assessProductionSpendPlan`，原文件第 391–486 行；宿主 `assessProductionScopePendingQuote` 与 `continueCoveredSpendApproval`。

**当前行为：**`requestedMaximumCents` 只累计判为 `execute` 的条目；出现阻断后，最终 `additionalCents` 和主要原因只取**第一个阻断项**。

### CG-04｜P1｜角度去重与候选 ID 使用不同身份定义

**位置：**`trend-opportunity-agent.ts::buildCandidate/candidateId/editorialAngleKey`；`trend-studio.ts::appendCandidateSources/mergeCandidateSupplements`。

**当前行为：**

`editorialAngleKey` 使用归一化后的 `title + audience + track`；`candidateId` 却只使用 `signalId + title`。因此同一信号、同一标题、不同受众的两个合法角度，会通过角度去重，却得到相同的候选 ID。反过来，不同事件的相同标题/受众/题材，又可能被不含事件身份的角度键合并。

候选 ID 不是纯展示字段：补充来源通过 ID 找第一个候选，补充记录也按 ID 关联。身份冲突会使选择和证据归属出现歧义。

**必须达到的合同与根因：**同事件允许多个实质角度，同时每个角度必须拥有可稳定寻址的身份。当前“是否重复”和“是哪一个候选”各用一套定义。

**唯一修复方向：**建立统一的“canonical event + editorial angle”身份投影，角度表达受众收益、核心问题/兑现及表现方向；同一投影贯穿去重、候选 ID、缓存及补源关联。标题是展示字段，`generationNonce` 是生成批次身份，二者都不能替代角度身份。

**最小回归集：**同事件同标题不同受众保留且 ID 不同；同受众不同收益保留；同角度仅修改展示标题不制造新身份；不同事件不误合并；向某一角度补源不污染另一角度；普通恢复保持身份、显式换批改变请求身份。

```text
模型标题：用3步整理桌面
结果：因来源标题没有数字3，被拒绝。
```

前者是带事实前提的问句，后者可以只是拟议的视频结构。这两类不应使用同一个词面规则裁决。这里证明的是选题 grounding 边界失效，**不是已经证明这些内容能绕过所有下游检查并发布**。

**必须达到的合同与根因：**不得把问号当作事实免责，也不能把所有常青方法、步骤数量都要求从热点标题逐字推出。根因是没有区分事件事实、待核验问题和创作结构。

**唯一修复方向：**将事件事实/问句前提、编辑角度和计划性结构分开表达与检查；事实按具体主张关联来源，问句前提同样核验；来源不足保留为明确待补证角度，而不是通过“grounded”认证。使用现有总编与 role-audit 承担语义核对，不新增第三审计模型。

**最小回归集：**虚构前提加问号；同一字段“断言＋问题”；没有数字的中文新增事实；有来源的数字被换主体/单位；合法三步法、节拍和假设比较；来源不足但可补源的角度仍可见且不被当成已核实事实。

---

### CG-06｜P1｜连续 `not_accepted/409` 绕过上界，形成无界会话重建循环

**位置：**`role-agent-loop.ts::executeOperation/untrackUnacceptedOperation`，原文件第 646–703、718–725 行。

**当前行为：**遇到 `not_accepted + 409` 后，代码删除 session、减少 phase attempt 计数、递增 request generation，然后直接 `continue`。这个分支没有独立的重建次数上限，也不推进语义 iteration。

原函数验证设置了：

```text
maxIterations = 1
maxPhaseAttempts.produce = 1
```

但连续 409 仍发出了 **5 个不同 requestId**；第五次是探针主动终止，而不是产品上限生效。这里证明的是无界请求/会话重建，不是已证明发生了重复扣费。

**必须达到的合同与根因：**已确证未受理允许安全恢复，但恢复本身仍必须有界。当前用“未受理不计模型执行次数”同时抵消了控制循环的停止条件。

**唯一修复方向：**为同一逻辑 operation 增加独立、可持久恢复的 session re-bootstrap 预算；允许一次受控重建，重复拒绝即停止并保留原因。不能通过扣减付费/模型次数计数来替代恢复上限，也不能对 uncertain 请求退休原 requestId。

**最小回归集：**一次旧 session 拒绝后成功；连续 409 有界停止；produce/audit 两分支；进程恢复后不能重置重建预算；uncertain 恢复仍绑定原 requestId；停止后不额外调用 backup 或重跑已完成 producer。

### CG-07｜P2｜总编声明的结构合同没有进入确定性校验，交付候选可能晚于审计被补造

**位置：**`trend-opportunity-agent.ts` 的 `currentRoleContract`、`parseModelIdea`、`buildCandidate`。

audit 上下文声明 `everyIdeaMustProvideSpecificVisualPlan: true`、评分必须为 0–100 整数；解析器却允许缺少 `visualPlan`，数值也使用宽松转换。缺失的 visual plan 随后在构建候选时通过 `planVisualDirection` 补入，形成“审计时没有、交付时才有”的方案。

**合同与根因：**当前角色声明为必需的交付结构，应在通过审计前真实存在；prompt 声明不能替代 parser 合同。

**修复方向：**按已声明合同验证具体视觉方案和整数评分；需要默认化的内容在审计前完成，并让 audit 看到最终候选。补缺字段、非法评分、默认方案及 checkpoint 恢复测试；相应升级合同版本，避免复用旧的 passed checkpoint。

---

### CG-08｜P2｜uncertain 调用仍向创作者建议“重试或选择其他模型”

**位置：**`codex-chat.ts::creatorMessageFor`，原文件第 641–666 行。

该函数不接收 acceptance stage。超时、网络错误和其他结果未知情形，仍可能输出“请重试或选择其他模型”；而底层恰恰将这些情况视为 uncertain，禁止开启替代请求。

**合同与根因：**用户文案应解释“请求可能已经受理、已保留什么、现在应核对哪个原请求”，不能仅凭失败类别建议换模型。当前文案丢失了 acceptance stage。

**修复方向：**让文案消费结构化 stage；uncertain 明确引导核对原请求并保留进度，只有已确证允许新请求时才提供重试/backup 建议。不要通过改文案放松底层恢复限制。

## 四、架构与产品收敛建议

现有方向无需推倒重建。数字人、口播、照片转视频和短剧应继续复用 **run 级许可、素材意图身份、逐请求物理账本、最终成片双审**，通过既有 Provider/worker 能力增加输入身份和产物类型，而不是为每种视频形态再建立一套授权、恢复或审计工作流。此处是后续扩展建议，不是对尚未提供实现的完成声明。
