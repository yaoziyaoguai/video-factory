# 已确定的产品与技术决定

本文件是恢复实施的决定集。执行者可以修正实现细节，但不能在没有新产品决策时重新选型或改变下面的含义。

## 1. 产品目标

VideoFactory 要提高生成有传播力视频的概率，同时让普通创作者容易理解、控制、修改和恢复制作。

“爆款能力”不是一个虚构分数，而是工作流持续提高以下质量：明确受众收益、具体开头吸引、内容持续推进、结尾兑现、画面真实可执行、声音自然、素材与承诺一致。模型高分不能代替完整成片证据和用户最终判断。

未来可能增加数字人、口播、照片转视频、短剧等方式。本轮只保护可复用边界，不实现这些产品，也不建立通用 Agent 平台。

## 2. 用户主流程

三个入口保持独立，由用户自己选择：

1. 热点：先提供有实质差异的创作方向，用户选择并补充要求。
2. 系列：选择本集，继承 Bible/Canon 并形成独立承诺。
3. 自有想法：直接表达想法，按需要完善，不强迫经过热点。

之后共用：形成制作方案 → 用户看方案和图片/视频最高授权 → 自动制作与质量检查 → 用户看成片并接受或提出修改。

内部可有 treatment、script、director、source search/rank、preflight、voice、render、technical review、dual review 等阶段，但不能把每个技术状态变成用户必须理解和确认的页面。

## 3. 创作协作

- 导演从构思阶段介入并对整片创作一致性负责，但不是每个事件都调用一次的旁观监督模型。
- treatment、编剧、导演和素材可得性共享一份可执行方案，字段所有权清楚。
- 时间是范围，不是固定 24 秒。实际长度由内容、动作和自然声音决定；范围内允许调整，但所有下游只读同一份当前 executable plan。
- 模板的 `storyStructure.required` 是叙事责任；`shotSlots` 通常是建议，不强制一槽一镜。
- 素材不可得或模型失败时停在可操作状态，绝不生成说明卡伪装成功。
- 局部修改只失效真实依赖闭包；已证明仍适用的画面、声音和审片证据应保留。

## 4. 双审与返工

- 最终由两个实际不同的 reviewer provider/model 独立审片。
- 两边互不可见，读取同一不可变 evidence snapshot；汇总是确定性的，不新增第三融合模型。
- 单分支失败只能有界补该分支；不能用单审发布，也不能为补审重渲染或重买素材。
- findings 必须能映射到 script/director/source/voice/edit/review/user 等责任和范围。
- 无法定位的用户反馈进入 `needs_scope` 一类可操作停顿，不自动扩大到全片，也不丢弃原反馈。

## 5. 费用与授权

- 取消全局硬费用上限；本片预算意向可选，默认不填，只影响方案取舍，不等于付款授权。
- 文本模型和订阅审片不弹现金审批。TTS 自动执行，并沿用后台人民币记账。
- 图片/视频在方案和报价可见后，由用户确认本次最高授权、模型/目标范围和有限付费修复。
- 授权金额是边界，不是必须花完的目标。授权内先满足确认的质量，再优先复用、选择同质量更省的路线。
- 额度不足或范围变化时，系统说明已完成成果、缺失目标、预计/最高追加、价值和调整方案差异；用户可追加、调整方案或暂不继续。
- 拒绝追加不等于同意降质。没有可行达标路线时停止申请钱，说明能力/证据限制。
- 已 accepted/unknown 的外部请求只核对原 task，不重发；未知费用保守占用，不能凭 UI 猜测“未扣费”释放。
- 原逐请求 spend authorization、ledger、lease、CAS 和 exact matcher 保留。新的 production scope 由可信宿主派生精确子凭证，不能以余额、role 或客户端字段绕过。

## 6. 架构边界

- 保留 React、Fastify、WorkflowRunner、ProductionPipeline、Python/FFmpeg worker 和现有 Provider 接入。
- LangGraph.js 只负责创作规划子流程；SQLite 只存规划 checkpoint，不保存业务授权、账本或媒体真相。
- FileRunStore 和现有 artifact/ledger 仍是正式 run、授权和副作用的权威记录。
- 不新增 Redis、微服务、队列、业务数据库迁移、第二工作流框架或第二前端状态机。
- 新 production 和新 derivative 使用 `joint-v1`。legacy 仅支持原历史 run 的读取/恢复；joint 失败不能 fallback legacy。
- GitHub Actions 是正式部署入口，阿里云是运行环境。不得用 SSH 手工覆盖生产代码。

## 7. 工作方式

- 每阶段先建立通用失败证据，再修同一根因的所有表象。
- 聚焦测试是实现反馈，不是外部审计。完成整个阶段后再做 Oracle Web 阶段审计。
- B4、B5、C1、C2 依次放行；不得在前置未通过时用下游兼容层遮住问题。
- 所有实现完成后集中本地 E2E 和一次统一审计；经当次授权后提交、GitHub 部署、云端桌面/移动 E2E。
- 不能用旧日志、mock 总数、单个 94 分报告或“代码已写”宣布完成。
