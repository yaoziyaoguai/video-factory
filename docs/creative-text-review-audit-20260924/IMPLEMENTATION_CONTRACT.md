# 实施合同：所有面向创作者的文字交付

本文件是执行端的产品语义合同。Oracle 原文见 `ORACLE_VERDICT.md`；若代码与这里的“当前状态”描述不符，先用测试和调用链证据更正现状，不得自行改动下面的目标行为。

## 0. 目标与边界

**目标**：每份需要创作者采用的模型文字交付都走“已确认上游 → 有效初稿 → 独立审计一次 → 稿件和内容建议同屏 → 人工决定”。用户可以直接采用、明确发送修订、主动再审，或者继续讨论。修订返回只停在新稿；不自动再审、不自动推进。

**不做**：不自动生成素材、不修改媒体 Provider 与模型全局设置；不造“审计的审计”；不把全部节点塞进 treatment/script/director 的同一状态机；不新建平行工作流引擎；不取消事实/来源/结构/素材许可/范围/费用/未知请求安全闸门；不更改历史 run 的事实或补造旧审计。用户质量风险决定不是付费授权。

### 节点矩阵（不得遗漏）

| Broker task kind | 当前交付归类 | 必须达到的行为 |
| --- | --- | --- |
| `topic-ideas` | 选题候选包，纳入 | 候选包初产审一次，显示内容建议；选中某一候选可同时成为该候选的明确采用，不再要求整包重复确认。选中记录候选 ID、候选包版本与当时审计状态。修订候选不自动审。 |
| `series-roadmap` | 系列路线图/单集计划，纳入 | 规划窗口初稿审一次，用户选集/采用绑定实际版本。已有开拍检查优先只审当前单集，不因质量建议自动重写用户已确认内容；Canon/Bible 硬冲突回用户处理。 |
| `creative-treatment` | 构思，纳入 | 初稿审一次再停；用户确认不临时补审。 |
| `script-draft` | 脚本，纳入 | 只用有效已确认构思为上游；初稿审一次；构思修改后旧稿留历史但不能冒充有效下游输入。 |
| `director-plan` | 导演方案，纳入 | 初稿审一次；`direction` 与 `material_plan` 两种决定身份分开。选材证据更新须重判选材接受，不重复审同一未变化创作稿。 |
| `publish-copy` | 标题/描述/标签，纳入 | 初稿审一次，支持手改、AI 修订、主动再审、采用与历史；文案采用不等于发布平台。`write()`/`writeDetailed()` 的生产消费者不得绕过这一交付合同。 |
| `reference-grammar` | 当前 Studio 可见、可编辑的参考片分析报告，纳入 | 启用该节点时初稿审一次并供用户看/采用；按 2026-09-26 用户裁决 b，支持手改、AI 修订、主动再审与历史，修订只产未审新稿，再审只追加当前版本审计、不换稿或失效下游。复用原参考视频证据并校验来源文件。若另有纯后台特征提取调用，记录调用点证据，不额外加停点。避免与简报确认重复。 |
| `role-audit` | 审计任务，不递归审 | 审计结果随目标稿版本展示并记录；简报审计同理。 |
| `asset-rank` | 素材排序分析，不新增完整流程 | 在现有选材方案中展示依据及不确定性，绑定候选证据；不能自动扩购或返工。 |
| `visual-review` / `audio-review` | 画面/声音评估，不递归审 | 报告绑定准确媒体版本，给用户看；重新审查和修改仍按现有明确决定及门禁。 |
| `creative-discussion` | 讨论/改稿子任务，不独立加停点 | 解释只回消息；备选只存备选；明确修订才更新原节点稿件，更新后标未审。 |

### 2026-09-26 审片耗时优化补充

云端 dogfood 证明视觉审片曾因报告补充建议自动执行第二轮产审（额外约100秒），并非视频返工。按用户本次优化授权，正式 Studio 的源素材预检和成片视觉审片默认完成“有效报告一次＋独立复核一次”就交回用户；复核 `repair` 保留为建议，不自动改报告、不虚构通过，用户要补查时仍走既有明确操作。结构无效与未知已受理请求沿用原有受控修复和恢复，不用无效结果冒充完成。

此策略仅作用于视觉审片的默认生产调用，不将所有 `runRoleAgentLoop` 全局改为单轮。旧检查点和已受理请求的身份、证据、调用上限不因提速重置；旧第二轮若已受理，先结清并保留真实结果，不开启第三轮。进度显示本次真实轮次，不再给新单次审片预告自动三轮。

交付边界仍是生成可下载视频、发布文案和素材清单；用户在站外手动发布，不要求配置平台自动发布，也不由 agent 替用户上传。发布文案采用仍不等于平台发布，已记录的采用接口409不得解释成缺平台账号。

直接生成图片、视频、语音等素材的 AGI Provider 不纳入本合同，但沿用既有报价、来源、质量和人工门禁。`brief` 是用户/宿主输入及其独立复核，不把审计本身当成模型创作稿。

## 1. 精确动作语义

### 2026-09-26 生成路线与终轮停点修复

构思中的获取责任明确区分 `pipeline_retrievable`（图库视频/图片）与 `pipeline_generated`（生成视频/图片），均使用既有 `retrievalProviderId` 绑定本次允许的对应能力。新生成路线只供 `illustration_only`，不能证明现实事实；“可生成”不等于已经取得素材或获得付款授权。Broker schema、提示词、语义校验、管线解析、就绪检查与页面文案必须同步；复用构思 schema 的讨论任务合同摘要也须更新。

就绪评估为 `revise_here` 时，达到允许的最后一轮（或显式审后停止）应交付原候选、原审计和宿主建议，由用户选择修改或承担建议后推进，不能继续越过循环上限报错。旧进程已落盘完整终轮、没有在途请求/待审候选/校验错误时，恢复只收口，不重复产稿或审计。不改写旧候选的路线，不重造请求身份，也不取消结构、事实、费用和未知请求保护。

| 用户动作/系统时机 | 本节点允许的模型调用 | 停点与状态 |
| --- | --- | --- |
| 初次生成 | 对有效初稿产稿一次、独立审计一次；**审计建议不驱动自动修稿**。结构无效时不发布可采用稿。 | 展示稿件＋全部有效内容建议，停给人。审计服务已核清失败则如实标“本版未取得审计结论”；未知已受理请求继续恢复原请求，不当成失败。 |
| 只讨论/解释 | 只允许消息，不允许改当前稿。 | 留在当前版本。模型返回 `intent: revise` 时宿主拒绝应用。 |
| 请求备选 | 可产备选，但不得替换当前稿。 | 比较后由用户采用；采用备选生成新的当前版本，未审。 |
| 明确发送修订 | 只产一次所授权的修订，不调用本版独立审计。 | 新版本、未审、停下；保留有效旧稿直至新稿通过结构/范围校验后原子应用。 |
| 手工保存/恢复旧稿为新稿 | 不调用模型审计。 | 新版本、未审、停下；恢复旧稿不是重新启用其旧审计。 |
| 主动审计当前版本 | 只独立审当前精确版本，不产稿、不推进。 | 记录本次结果，仍停下；保留历史审计。 |
| 明确采用当前稿 | **本节点模型调用 0**；做所有确定性硬校验，记录用户看到的审计状态。 | 进入既有下游；下游自己的“初稿＋首审＋停点”不是当前节点重复审计。 |
| 返回上游 | 不删除历史稿和已存在媒体。 | 受影响下游的有效确认/审计适用性/报价引用失效，下一有效阶段仍须人确认。 |

审计 `repair` 是建议，不是模型否决权；用户可明确承担质量建议并采用。用户也可采用本版未审修订稿，但决定必须记为“未审采用”，不可伪造 `pass`、旧分数或 `checkIdentity`。审计**已完成但无结论**与**请求仍未知/可能仍运行**要严格区分；后者不可新发同一付费请求或随意跳过。事实/来源/许可/结构/已批准返工范围/费用仍可挡住推进。

## 2. 最小持久合同（复用现有 run、series、候选与 artifact 存储）

不要只扩充 `CreativeStage` 的枚举。可以抽取小型共享值对象/校验函数，由不同节点适配现有存储；同一节点的当前稿、审计和决定必须有共同身份。

1. **稿件版本**：节点实例 ID 与 purpose、不可变 `versionId`、内容 hash、逻辑 `artifactId`、不可变内容快照或不可变快照引用、输入摘要、已确认上游版本引用、相关媒体/证据摘要、产生方式与 `commandId`。逻辑 `artifactId` 可保持兼容，但不能用其原地变化内容充当旧版全文。
2. **审计记录**：不可变 `auditId`、目标 `versionId` 与 hash、送审输入/证据摘要、独立操作身份与实际模型/Provider、合同版本、完成/未完成状态、完整机器结果、面向用户的建议。A→B→A 的 V1 审计不能回挂 V3；相同文字不等于同一版本。
3. **用户决定**：目标版本、用户当时看到的 `auditId` 或“本版未审”、是否明确承担建议/无审计风险、操作者、时间、`commandId`。`direction` 和 `material_plan` 分别记录；质量接受与素材费用授权分开。
4. **命令回执**：`commandId`、规范化请求体摘要、预期状态版本、执行状态、外部请求身份、结果引用、可恢复错误。重放先查回执：同 ID 同 body 返回原结果，同 ID 异 body 冲突；新命令再做 stale 校验并原子登记。

结果落盘须再次核对节点/purpose、目标版本、输入摘要和操作身份；迟到结果只能归历史，不能覆盖当前稿。重启后对已受理请求观察原 `requestId`，不重复创建或重复扣费。已有 checkpoint、prepared operation、resume 路径必须复用。旧 run 没有证据时显示“历史信息不足/未审”，打开/迁移时零模型调用；旧在途请求按原回执恢复，到安全停点才切换合同。

## 3. 审计文案与 UI

保持现有桌面稿件/讨论双栏和移动端两个视图，增加可见的“本版建议”与历史切换，不重做整个工作台。标题写真实版本（不是每条消息都会增长的 `reviewRevision`）与真实状态：`本版已审计`、`本版未审`、`审计中`、`审计未取得结论`；`pass` 下只要有有效建议也要展示。旧审计只能标“上一版意见”。

审计同一次输出保留机器字段 `criterion/evidence/repairInstruction`、`planningDisposition` 等，新增面向创作者的内容字段（建议标题、观众/作品中的具体观察、可执行改法）。新输出必须具体说**观众会看见/听见什么、哪里不顺、怎么改**；旧数据缺这些字段时做保守的可读投影，不为翻译再额外调用模型。按仓库合同版本和 digest 更新规则同步 Broker、Pipeline、跨进程测试。各角色审计重点：选题的观看理由与事实来源；系列的单集兑现与连续性；构思的观众承诺/叙事路线；脚本的开场、旁白时长与事实表达；导演的画面连续性、路线可执行性与声音衔接；发布文案与成片事实一致；参考报告区分已观察与推断。内部字段留机器层，不在用户建议标题中原样输出。

审计建议提供复选框；“加入修改意见（N）”将所选建议**追加**到已有输入，不覆盖、不自动发送，用户可删改并增写后按“发送修订意见”。一条建议绑定 `auditId + versionId + issueId` 供追溯，但最终修订要求仅以用户实际发送的编辑框文本为准。讨论范围多选与审计建议多选是两个控件。换稿/切节点清掉旧目标选择并检查待发输入的身份，不把旧建议默默施加于新稿。消息上限 4,000 字符：超限阻止发送并提示删减，原输入原样保留，不静默截断。快捷提示按钮也不能覆盖已有未发送文字。

主动作分开：`发送修订意见`、`审计当前版本`、`采用当前稿，继续`。有建议而用户直接采用时明确显示“保留这些建议，仍采用”；未审时显示“采用本版（未审计）”。这两种质量决定不需再叠一层泛化确认，但现有素材风险、返工范围、费用等专门确认继续保留。历史视图能看全文、该版审计及当时决定；历史版不显示可误确认当前版的按钮，恢复旧内容须创建新版本并重新校验。

## 4. 返工范围故障必须同批修复

现有事故：原 run 零媒体，批准 `affectedScenePositions=[]` 且七镜 `retain`；新规划产出五镜，前五镜视觉意图变化；早期按未物化素材推断空范围放行，worker 的 `reworkAffectedScenePositions` 最终抛错。**零媒体不等于零内容影响；不能删 worker 校验，也不能把 `[]` 解释为全部允许。**

基于旧计划与候选计划（非媒体数量）确定 `ReworkImpact`：旁白/视觉意图/获取路线差异、增删重排镜头、全片视觉/节奏/声音规则变动、`retain` 内容变化和依赖闭包。优先复用现有镜头身份；只有 position 时冻结旧基线映射，对结构变动显式报冲突，不猜对应关系。四处检查：规划前、阶段候选成为当前稿前、人工保存/采用时、报价与媒体提交前。越界候选可保留为未采用提案，但不得替换有效稿、不得提交媒体请求。

可恢复界面只给两种明确方向：①保留可验证的旧七镜方案；②展示实际差异后由用户重选允许改动的范围，再按变化重新报价。范围决定、稿件采用、费用授权是三件事。无基线映射、事实/许可/来源不成立、未知已受理请求、授权不匹配时不能靠质量接受按钮放行。已 `failed` 的旧运行保留失败记录，以结构化范围冲突码经显式恢复动作进入决策停点；不吞任意 worker 错误，不按中文错误字符串泛化恢复。

## 5. 实施边界与建议顺序

`S0` 先补全未附 Oracle 的调用链：`apps/codex-broker/src/task-definitions.ts`、`packages/production-pipeline/src/role-agent-loop.ts`、`creative-planning.ts`、`production-pipeline.ts`、`reference-grammar.ts`、`apps/studio/src/server/production-studio.ts`、Studio API/types/store、各节点消费者与测试。记录每个任务的产物去向、用户停点、默认轮数、checkpoint 与费用。不能把 Oracle 的未验证推测当线上已发生事实。

`S1` 先写失败测试再做版本/动作/回执最小合同（主责 `creative-review.ts`、必要的共享值对象与现有存储/API），保留已有 stale、检查身份、保存失败安全行为。`S2` 修返工范围预检、人工恢复和 worker 最后防线。`S3` 将 treatment/script/director 接到新合同。`S4` 接入 topic/series/publish/reference 四类其他内容交付，不能只交三阶段。`S5` 做同屏建议、内容文案、历史回看。`S6` 完成全量回归和真实本地应用 QA。可以按 S1–S5 小步实现，但**最终交付必须一次覆盖全部节点和返工安全**；任一子阶段测试失败不跨过去宣称完成。

避免全局把 `runRoleAgentLoop.maxIterations` 改成 1。应以调用目的实现“首稿产审一次／修订只产／主动审计只审”；视觉审片默认按上方2026-09-26补充首审后交回用户，其余内部分析路径维持有界循环与恢复。所有变化都要检查 source/dist、合同 digest、原有费用/恢复测试。
